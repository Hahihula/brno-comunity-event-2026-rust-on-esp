Quick framing before we start. Two promises: One, that Rust is taken seriously at Espressif, not a hobby project. Two, that by the end you know the exact three commands that get you from nothing to a running firmware. Nothing else. If you only remember one slide, remember the last one.
Where things stand

Rust is a first-class citizen

Not a community experiment, not a wrapper around C. Espressif officially supports Rust as a first-class development language, alongside ESP-IDF.

  • Own HAL, own drivers, own tooling — built and maintained for ESP chips
  • Stable API, not pre-v1-releases
  • Documented, versioned, and released alongside the silicon
The honest caveat

It is a little bit behind the C SDK.

ESP-IDF is the reference SDK. It reaches new chips and new peripheral features first, and it has the deepest example coverage.

Lets say the caveat out loud — ESP-IDF is the reference SDK, and it will always be first to a new chip or a brand-new peripheral. Rust is a little behind that frontier.
So which one?

Pick the boring answer

Cutting edge

ESP-IDF (C)

You need a peripheral or chip feature that shipped last week, or you are porting vendor middleware. Go here first.

OR
Everything else

Rust

For the overwhelming majority of projects, Rust is simply the better tool — and it is genuinely production-ready today.

The gap is measured in months, not years — and it closes with every chip release.

Rule of thumb: if you are chasing a datasheet feature from this quarter, use ESP-IDF. For everything else, Rust is not a compromise — it is the better default.
Why you'd choose it

What you actually get

Safety

No memory bugs

Ownership and borrow checking kill the buffer overflows and use-after-free that dominate embedded CVEs.

Tooling

Cargo does the work

Dependencies, builds, tests, docs, linting and cross-compilation — one tool, no hand-rolled Makefiles.

Scale

Async that fits

Embassy gives you async on a microcontroller, so Wi-Fi and sensors stop fighting each other.

Simulation

Wokwi, built in

Works seamlessly with the Wokwi simulator — from the CLI and from VS Code.

Plus: the type system catches a whole class of logic errors at compile time, and the crate ecosystem is shared with the rest of Rust — not reinvented per vendor.

Three benefits, one breath each. For the C people: you stop owning the memory-safety argument. For the Rust people: Cargo plus a real crate ecosystem full of no_std ready linraries for lot of sensors and other parts. And async is the one that actually changes how you write firmware — Wi-Fi and sensor work stop being callbacks. Bonus: it all works seamlessly with the Wokwi simulator, from the CLI and from VS Code — no board needed to try it.

Getting started

Three steps: toolchain, flasher, project generator.

Halfway point. Everything so far was context, everything from here is something you can type tonight. Three moving parts — toolchain, flasher, generator.
Step 1 · Toolchain

You already have the hard part

Assume rustup is installed. If it isn't, rustup.rs is one command — but from here on, Rust just works.

RISC-V parts

Mainline Rust — you're done

The C-series, H-series and P-series are standard RISC-V. A normal stable Rust toolchain targets them. No extra install.

Xtensa parts

You need espup

Xtensa has no upstream LLVM backend, so espup builds and installs the toolchain for you.

ESP32ESP32-S2ESP32-S3 
$ cargo install espup --locked
$ espup install
$ # then, in every new shell: . $HOME/export-esp.sh
The single most common question, so answer it precisely. RISC-V is standard, so stable Rust handles it and you need nothing extra. Xtensa is not an upstream, so espup installs a purpose-built toolchain. espup does everything — you just run it.
Step 2 · Flashing

Getting code onto the chip

Option A

cargo-espflash

Pure Rust, lives next to cargo build, and gives you a monitor as well as a flasher.

Option B

esptool.py

The one that ships with ESP-IDF. If you already have IDF installed, it is right there and it works fine.

$ cargo install cargo-espflash --locked

# board-info, monitor, erase, read-flash, save-image — the whole serial toolchain
$ cargo espflash board-info
Lead with cargo-espflash: it lives in the same mental model as cargo build, and board-info is the first thing to run when unsure what board you are holding. Both are legitimate though — if IDF is already on your machine, esptool is right there and there is no reason to change.
Step 3 · Project

esp-generate does the scaffolding

The easiest way in. A terminal wizard asks a handful of questions and writes you a real, buildable project. 

$ cargo install esp-generate --locked
$ esp-generate

Sync or async

Plain blocking code, or embassy async — your call.

Target chip

Any supported ESP SoC, selected from a list.

Wi-Fi init

Optional radio bring-up, wired in from the start.

Let me be clear, you are still cross-compiling and setting up the project so cargo knows exactly what to do may be a pain. esp-generate solves that for you. One command, and you have a compiling, flashable project with the right target triple and the right HAL already wired. Sync or async is a menu choice, and Wi-Fi initialisation is a checkbox. If people want scripting, there is a headless mode with -o flags — so even you AI agents will quickly learn how to use this.
Step 4 · Ship it

Build, flash, done

$ cargo build --release
$ cargo espflash flash --release
$ cargo espflash monitor

Same verbs you already use for every other Rust project — just pointed at a microcontroller instead of a server.

The loop closes. Cargo build, flash, monitor. No Makefile, no CMake, no separate flashing script, no second toolchain to learn. If you have written Rust before, you already know how to do all of this — that is the entire point.
The whole thing

Three commands

1esp-generate   ← scaffold the project
2cargo build   ← compile the firmware
3cargo espflash flash   ← write it to the chip

Rust on ESP is as easy as esp-generate, cargo build and cargo espflash flash.
